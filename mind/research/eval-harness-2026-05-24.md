# Long-term-memory benchmarks for Chimera — research note (2026-05-24)

**Scope**: Phase 4 #8 of the Honcho-inspired roadmap ([ADR 0123](../../docs/adr/0123-honcho-inspired-enhancements.md)): *"LongMemEval / LoCoMo benchmarks — integrate the eval harness (run their evals; don't port)."*

This note is **research-only**. No ADR, no code. The goal is to lock the integration plan before any chip writes a line of harness adapter — the lesson from PR #41 is that scope creeps when implementation precedes the writeup.

The Chimera-side lens is **"which memory surfaces are testable today?"** The note surveys two public benchmarks against Chimera's actual memory layer and recommends an order plus a smallest-viable integration point. A future chip files the ADR and ships the integration.

## The two candidate benchmarks

### LongMemEval

- **Source**: Wu et al., *"LongMemEval: Benchmarking Chat Assistants on Long-Term Interactive Memory"* (ICLR 2024).
- **Repo**: https://github.com/xiaowu0162/LongMemEval (MIT).
- **Shape**: 500 manually-curated question-answer pairs. Each item has a synthetic conversational history of ~50 sessions / ~115 turns / ~115K tokens preceding the question. The system under test must answer the question using whatever memory it kept from the history.
- **Five task categories**:
  1. **Single-session-user**: fact embedded in one prior session.
  2. **Single-session-assistant**: fact stated by the assistant in one prior session.
  3. **Multi-session**: information must be combined across sessions.
  4. **Knowledge-update**: a fact stated early is corrected later; the system must use the corrected value.
  5. **Temporal-reasoning**: question requires reasoning about *when* something happened.
  6. **Abstention**: question whose answer is *not* in the history; system must say so.
- **Scoring**: model-graded correctness (LLM judges answer against reference) + a calibration set. Released harness produces a single accuracy-per-category table.
- **Hardware floor**: the histories are large but read-only; no fine-tuning. ~$5–$20 of inference per full sweep depending on judge model.

### LoCoMo

- **Source**: Maharana et al., *"Evaluating Very Long-Term Conversational Memory of LLM Agents"* (ACL 2024).
- **Repo**: https://github.com/snap-research/locomo (BSD-3).
- **Shape**: 50 multi-session conversations of ~600 turns / 9,000 tokens each. Each conversation is between two AI agents with assigned personas, generated by a controlled-persona pipeline. Three downstream tasks built on top of the conversations:
  1. **Question answering** — factual recall over the conversation.
  2. **Event summarisation** — produce a chronologically-ordered timeline.
  3. **Multimodal dialogue generation** — generate the next response consistent with the persona and history (uses image grounding from a subset of dialogues).
- **Scoring**: F1 / ROUGE / BLEU for the three tasks plus a model-graded persona-consistency score.
- **Hardware floor**: conversations are smaller than LongMemEval's per-item; the harness is bigger because three tasks compound. ~$10–$30 of inference per full sweep.

## Comparison against Chimera's memory subsystem

The Chimera-side surfaces available today, mapped to what each benchmark exercises:

| Chimera surface | What it stores | LongMemEval relevance | LoCoMo relevance |
|---|---|---|---|
| `CHRONICLE.md` (ADR 0003) | Per-day morning discovery / midday curiosity / evening reflection narrative | High — fact retention across days | Medium — narrative, not turn-by-turn |
| `mind/peers/*.md` (ADR 0128) | Per-peer trust + recent decisions + KFM snapshot | Low — peer-state, not conversation | Medium — persona-adjacent |
| `mind/peer_beliefs.jsonl` (ADR 0132) | Observer/observed belief labels | Low | Low |
| `mind/reflection_conclusions.jsonl` (ADR 0124) | Typed conclusions from Reflection engine | High — structured fact store | Low |
| `mind/wiki/` + FTS5 BM25 (ADR 0080) | Free-text wiki search | High — direct lexical retrieval | Medium — retrieval, not generation |
| `chimera/a2a/peer_trust_journal.py` | ALLOW/DEGRADE/REFUSE per peer | Low | Low |
| Dialectic API (ADR 0133) | Grounded Q&A surface | High — natural fit | Medium — Q&A task is matched |
| Trust / drift / ladder state | Operational state | None | None |

Two observations:

1. **LongMemEval lines up with Chimera's strengths.** Information retrieval from extended history (FTS5 + reflection conclusions), structured fact tracking (deriver schema), and Q&A surface (dialectic API). The "knowledge update" category maps directly onto Chimera's state-transition / drift-detection machinery (ADR 0028, ADR 0037). The abstention category maps onto the dialectic API's "no recorded information" stub framing (ADR 0133).
2. **LoCoMo's centre of gravity is dialogue generation and persona consistency.** Chimera is an agent that *consults* memory, not one that *generates* persona-consistent dialogue at length. The multimodal task is entirely out of scope (Chimera has no image-grounded memory layer). LoCoMo's question-answering subset is the only directly-testable axis today, and LongMemEval covers that axis with more variety and a cleaner harness.

## Recommendation

**Integrate LongMemEval first.** Reasoning:

1. **Five categories map cleanly onto five distinct Chimera surfaces** (single-session → FTS5; multi-session → reflection conclusions; knowledge-update → state transitions; temporal → cycle/timestamp metadata; abstention → dialectic stub). Each category gives an independent signal.
2. **The released harness is a thin Python CLI** that consumes a system-under-test endpoint. Chimera fronts this with the dialectic API (ADR 0133) — the assembled-prompt return shape is what the benchmark already expects from a memory-augmented chat system.
3. **The "knowledge update" category** is unusually well-suited as a regression for ADR 0037 (drift composite) and the state-transition machinery — failing this category should map directly to a Chimera bug, not a "Chimera doesn't do this" gap.
4. **Cost is bounded.** A full sweep is ~$5–$20 of inference; sub-sweeps (one category at a time) are well under $5. Fits within existing per-cycle / rolling-hour caps (ADR 0072 / 0076).
5. **LoCoMo's primary signals (persona consistency, multimodal grounding) are misaligned with Chimera's mission.** Running LoCoMo's QA subset alone is possible but adds the same signal LongMemEval gives with more noise.

**Defer LoCoMo to a follow-up.** Integration as a secondary benchmark makes sense if (a) we add a persona / character layer to Chimera (not currently roadmapped), or (b) LongMemEval saturates and we need a harder benchmark. Until then, the value-to-effort ratio doesn't justify the second harness.

## Smallest viable integration point

When the integration chip lands, the smallest viable shape is:

1. **A `chimera/evals/longmemeval.py` adapter** that:
   - Reads a LongMemEval item (history + question).
   - Loads the history into Chimera's memory surfaces (CHRONICLE / wiki / reflection conclusions) via a one-shot bulk-ingest helper. The ingestion is the bulk of the new code.
   - Issues the question to the dialectic API (`chimera peers ask self "<question>"` semantically).
   - Returns the answer in the shape LongMemEval's grader expects.

2. **A `chimera evals longmemeval` CLI verb** that:
   - Iterates the benchmark items.
   - Calls the adapter per item.
   - Writes per-item results to `mind/evals/longmemeval-<timestamp>.jsonl`.
   - Optionally runs the LongMemEval grader and prints the category accuracy table.

3. **A research-grade subset switch** (`--subset multi-session`, `--n 50`) so smoke tests can run in seconds without a full sweep.

4. **The harness lives at version-pinned `longmemeval @ git+...`** in `pyproject.toml` extras (`eval`). Operators opt in by installing the extra; the dep is not on Chimera's hot path.

**Out of scope for the integration chip**: persistence of historic eval results beyond the JSONL (no dashboard widget yet), automatic cadence runs (operator-invoked only), comparison-vs-baseline tracking. Each is a separate follow-up.

## Named follow-ups for the integration chip

In rough priority order:

1. **Bulk-ingest helper.** Convert LongMemEval session JSON into Chimera's memory surfaces. The trickiest part: do we re-run the Reflection engine over the history to get deriver-style conclusions, or load synthetic conclusions directly? The honest answer is "re-run the engine" — that's what the benchmark is testing.
2. **Adapter contract.** Shape of the function the harness calls into. Likely `answer(question: str) -> AnswerWithProvenance` where provenance is the `sources_used` list from the dialectic API.
3. **Grader configuration.** LongMemEval defaults to GPT-4-class judges; we should also support claude-sonnet-4-5 (cheaper, in-house). Cost report per sweep.
4. **`mind/evals/` directory** as the result substrate — mirrors `mind/peers/`, `mind/reflection_conclusions.jsonl`. Operator-grep-able JSONL per run.
5. **CLI verb `chimera evals longmemeval [--subset CAT] [--n N] [--judge MODEL]`.** Sibling of `peers`, `trust`, `escalations` in the existing parser.
6. **Per-category baseline note.** Once we have one full sweep, write down the score per category to `mind/research/longmemeval-baseline-2026-XX-XX.md` so future PRs can claim "+5% on temporal" with a number to point at.
7. **LoCoMo QA subset as comparison check.** Only after LongMemEval stabilises. Treat as a sanity comparator, not a primary benchmark.

## What this note explicitly does NOT decide

To keep the scope discipline that PR #41's review enforced:

- **No code.** This note ships alone.
- **No ADR.** The ADR lands with the integration chip; the chip's review pass is the right moment to lock the surface (judge model, JSONL schema, harness pinning).
- **No CLI namespace reservation.** `chimera evals` is the obvious slot but not registered until the integration chip wires it up.
- **No PyPI extra reservation.** `[eval]` is the obvious name but not committed in `pyproject.toml` until the integration chip.
- **No dashboard widget.** Result surfacing is the second follow-up after the integration chip lands.
