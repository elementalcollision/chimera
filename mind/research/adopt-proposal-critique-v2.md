## Cross-witness critique

- **(i) Under-implemented claim:** The "single most under-implemented" framing is false by the proposal's own matrix. Proposer-Quality Scoring and Drift/Anchor Primitives are exactly tied — each has 0 first-class, 1 partial (both Chimera), and 7 absent across the 8 frameworks (score=1). The proposal's dismissal of drift as "downstream" of proposer quality is a causal assertion with zero evidence: drift detection can operate on output distributions, token-probability shifts, or tool-call patterns without any proposer-quality infrastructure. This is rank selection bias — the proposal picks the tie that flatters its own thesis. Worse, Chimera is ✗ on Trust Gating/Attestation (score=3 field-wide, with 3 other frameworks having partial implementations), meaning the Trust & Quality column has a larger Chimera-native gap the proposal ignores entirely. The "single most" superlative is marketing, not measurement.

- **(ii) Scoring honesty:** The scores are self-serving in two dimensions. Implementation cost at 2/5 understates reality: the heuristic function alone may be ~150 lines, but the proposal lists 8 files touched, a DB migration (`ALTER TABLE mutations ADD quality_score REAL`), FTS5 index maintenance for the chronicle similarity check (which isn't free — FTS5 queries against a growing chronicle table will require index strategy and performance testing not accounted for), CLI changes with JSON output, 12+ test cases spanning unit/integration/regression/edge, and coordination across three different `create_mutation` hook sites. Realistic cost is 3/5 if everything goes smoothly, closer to 3.5/5 when the FTS5 performance tail is discovered. Alignment risk at 3/5 is understated: the proposal says scores are "advisory only" and "never blocks `create_mutation`," but the entire operator-value thesis is that scores will sort/triage/filter the proposal feed. The de facto gate arrives before the de jure one — the moment operators start ignoring low-scored proposals without reading them, the heuristic has hardened. That's not a hypothetical; the proposal anticipates it in "expected mutation type #4" (operator behaviour diverging from scores) without a remediation mechanism. This is closer to 4/5 alignment risk given the asymmetry between stated intent (advisory) and designed effect (attention routing).

- **(iii) Most likely failure mode:** The cold-start problem is the sharpest crack. A new proposer gets acceptance_rate=0.5 (default), novelty=0.5 (no chronicle history), producing exactly 0.4×0.5 + 0.3×0.5 + 0.3×(1−complexity_penalty) — if complexity_penalty is also 0.5, that's 0.5 overall. The proposal says empty payloads also default to "~0.5." So a brand-new proposer submitting an empty payload and a brand-new proposer submitting a brilliant, well-scoped proposal get indistinguishable scores. The score is maximally uninformative exactly when it's most needed — for new proposers the operator has no priors about. Second: the FTS5 similarity check for novelty is a text-keyword match against chronicle entries, not semantic similarity. A proposal containing boilerplate like "proposes to add" will match chronicle entries and be scored low-novelty regardless of substance, while a genuinely bad proposal with unusual phrasing gets a novelty boost. Third: the complexity penalty punishes all large diffs equally — a necessary database migration and a reckless config rewrite get the same penalty, creating false negatives the operator must learn to ignore. Fourth: the chronicle-driven feedback loop (expected mutation type #4) that would recalibrate weights when operator decisions diverge from scores is not in the implementation. The weights are frozen at 0.4/0.3/0.3 with no automatic tuning. The feedback loop exists only in prose.

- **(iv) Stronger alternative gap:** Trust Gating / Attestation — Chimera is ✗ (no implementation) while three other frameworks already have partial attestation (LangGraph, AutoGen, OpenAI Agents SDK). Operator value: 4/5. In a multi-agent system where sub-agents spawn across providers and peers federate, knowing *who* made a tool call or mutation is a hard prerequisite to any trust decision — including proposer-quality scoring. You cannot meaningfully score a proposer's quality if you cannot cryptographically bind proposals to proposer identities. The proposal itself acknowledges Chimera has "peer discovery & federation" (~) and "sub-agent spawn across providers" (✓) — both presume multi-agent trust without the attestation primitive that makes them safe. Implementation cost: 3/5 (requires x.509 or JWT-based agent identity, a `proposals.signed_by` column, and verification at the mutation gate — more plumbing than a heuristic, but well-understood cryptography with existing libraries). Alignment risk: 2/5 — attestation is an identity primitive, not a normative judgment; it doesn't encode opinions about "good" proposals. This beats proposer-quality scoring (4/2/3) on both alignment risk and on being architecturally prior — you need attestation to make the acceptance-rate gate (ADR 0090) trustworthy across a federated system, and you need it before any score becomes meaningful.

- **(v) Data that would change my mind:** Over 30 days, collect from the chronicle for every `create_mutation`: `mutation_id`, `quality_score` (even if computed retrospectively), `proposer_type`, `operator_decision` (accept/reject), `decision_latency_ms` (time from proposal display to operator action). The dispositive metric is AUC of quality_score predicting operator rejection — if AUC > 0.75, the heuristic has genuine discriminatory power and this gap is real. If AUC < 0.55, the score is noise and the gap is illusory. Secondary: decision latency by score quartile — if proposals with quality_score > 0.8 show mean latency ≥50% lower than those near 0.5, the score is saving attention (the entire value proposition). Tertiary: calibration plot — fraction accepted per score decile must be strictly monotonic. If any of calibration, AUC, or latency fails, the heuristic doesn't capture what operators actually value and the implementation cost (even at 2/5) is wasted. I would also want to see the cold-start cohort separated — if new-proposer scores have AUC < 0.6 while established-proposer scores have AUC > 0.8, the cold-start failure mode is confirmed and the heuristic needs a redesign before deployment. If all three signals pass threshold within 30 days, I withdraw my objection. If any fails, the right move is to build Trust Gating / Attestation first and revisit scoring when operator decision data has cryptographic provenance.
