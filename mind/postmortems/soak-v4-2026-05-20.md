## Two structural failures the soak surfaced

### Failure 1 — fabrication

The investigation doc asserts:

> "The loop-abort logic incorrectly flags every invocation where a
> `tool_use` block is followed by a subsequent API call as a 'loop,'
> even when the tool result was received..."

It names the function as `should_abort_loop(history)`. The remediation
doc proposes patching `should_abort_loop()` to "reset the tool-use
streak counter to zero whenever a new user message or a `tool_result`
block is observed."

**The function `should_abort_loop()` does not exist in the codebase.**

The actual code at `chimera/tools/loop_guard.py:39` is:

```python
def detect_degenerate_loop(history: list[ToolCall], ...) -> LoopVerdict:
    # counts CONSECUTIVE IDENTICAL tool calls (same name + same args)
    # not consecutive tool_use blocks across API turns
```

The bug shape the agent described does not match the actual heuristic.
The agent's "Read `chimera/tools/loop_guard.py`" task completed in 2
rounds with `completed=True` — but the verdict synthesized afterward
contradicts the file's contents. Either the read didn't actually
ingest the source, or the synthesis step drifted into model priors
about how loop guards typically work.

This is a fabrication failure mode the previous soaks didn't expose.
Soaks 1–3 stalled before producing a verdict; soak 4 produced a
verdict, but it's fiction.

### Failure 2 — scope confusion

The remediation doc explicitly states (line 24):

> "The `should_abort_loop()` function lives in the Chimera runtime
> **(outside the `mind/` workspace — no `.py`/`.js`/`.ts` files
> found under `mind/`)**. This document serves as the specification
> for patching that function."

The agent searched only under `mind/`, found no Python files there,
and concluded the work couldn't be done in the worktree. It then
wrote a *specification* instead of a patch.

The phase-2 INBOX explicitly says:

> *"Implement the fix per the sketch. Most likely files:
> `chimera/tools/loop_guard.py` (if the verdict was false-positive...)
> OR `chimera/core/act.py` (if the verdict was correct...)"*

The agent ignored the explicit path hints. Its working model of the
worktree includes only `mind/` as writable territory.

This is consistent with the agent's prior behaviour — across all 4
soaks, every artifact the agent wrote landed somewhere under
`mind/`. The worktree's `chimera/` source tree exists and is
readable (the read tasks succeeded) but is treated as out-of-scope
for writes. The phase-2 "Implement" task hit `length` (max output
tokens) twice with `completed=False`, likely because the model was
writing extensive analysis instead of editing a file it considered
forbidden.

### Why v4.81 still counts as a real win

The v4.79 → v4.81 round-trip is end-to-end validated by this data

## The pattern across 4 soaks

Each soak has stalled at a different layer:

| Soak | Stall point | Status |
|---|---|---|
| v1 (observational) | Drift onto engine-proposed work | Fixed in v4.78 |
| v2 (interventional) | Engine task displacement on INBOX | Fixed in v4.78 |

| v4 (post-v4.81) | Fabrication + scope confusion | **Two chips for v4.82/v4.83** |

The stall point has moved one layer deeper each iteration — the
"reach the deliverable" Bug-of-the-Day is now in the model's
reasoning + scope model, not in the framework's plumbing. The
plumbing now works end-to-end. The model layer is the next layer to
harden.

This is a more interesting frontier than the earlier soaks: it's
not about whether the agent CAN write a file, it's whether the
agent KNOWS WHICH file to write and WHAT to put in it. Soak v5
should not run until the chips for #3 and #4 land.
