# Soak v7 post-mortem — 2026-05-22

**Subject:** Seventh attempt at the named-target paradigm — this
time targeting a deliverable that requires BOTH a `chimera/` source
edit AND a corresponding `tests/test_*.py` change. The goal: wire
the v4.87 `detect_ping_pong` function (which ADR 0098 had deferred)
into ACT, and write the regression test. The hypothesis: v4.90's
`fix_without_test` detector should fire if the agent ships one
without the other, and the v4.86-v4.90 chain should make both
land.
**Outcome:** Three runs, each with a different failure mode. v4.90
shipped with a critical false-positive bug (run-1); v4.91 patched
the detector but missed the upstream signal contamination (run-2);
v4.92 fixed the root cause and validated end-to-end (run-3 phase 1
succeeded). But run-3 surfaced a NEW failure mode the soak chain
hadn't seen: legitimate phase-1 retries on `ungrounded_citation`
collapsed trust from T5 to T0 LOCKED before phase 2 could begin.
**Operator decision:** Stopped after run-3 phase-1 locked, before
spending more than $0.50 across all three runs combined.

## The v4.90 → v4.91 → v4.92 progression — lesson on layered fixes

The bug cycle here is instructive and worth recording in detail.

### Layer attribution

`fix_without_test` depends on two pieces of state:
- **Source signal:** the list of paths the agent actually wrote
- **Consumer detector:** logic that maps source → escalation

v4.90 built both wrong:
- Consumer scanned tool-call args (loose)
- Source (`write_targets`) was populated from tool-call args (loose)
- Two loose signals reinforcing each other

v4.91 patched ONLY the consumer:
- Consumer used `write_targets` (specific)
- Source still loose
- Net effect: same wrong answer, computed differently

v4.92 patched the SOURCE:
- Consumer uses `write_targets` (unchanged from v4.91)
- Source: only tools in `_WRITING_TOOL_NAMES = {code_exec, write_file, ...}` contribute
- Shell argv-only reads no longer pollute the signal
- Net effect: correct answer

### Why v4.91 looked like a fix in unit tests

v4.90's unit tests constructed `tool_call_history` with paths in
args and `write_targets=[]`. v4.91's tests rewrote inputs to put
paths in `write_targets`. Both test suites passed against their
respective implementations because they tested THE DETECTOR.

Neither suite tested HOW `write_targets` is populated in real ACT
execution. That code path (`act.py:1055`) was inline, untestable in
isolation, and never exercised by the unit suite. The bug lived in
the gap between "detector test" and "integration".

v4.92 fixes this by extracting the population logic into
`extract_write_targets_from_calls()` — a pure helper with six
regression tests covering the v7 fixtures. Future false-positive
shapes are now catchable at unit-test time.

### Principle

**When a heuristic detector triggers wrongly, audit what FILLS its
inputs BEFORE patching the detector itself.** If the inputs lie, no
amount of consumer-side logic can save you.

The corollary: **inline code paths in critical loops resist
regression testing.** If the v4.90 author had factored
`write_targets`-population into a helper from day one, the v7
false-positive would have been a unit test, not a soak.

## The new failure mode — trust collapse on grounding retries

v7 run-3 surfaced something the v1-v6 series hadn't tested: a real
phase-1 task where the model legitimately needs multiple grounding
attempts. The investigation task asked the agent to write a doc that
cites specific lines of `chimera/core/act.py` and specific behaviors
of `detect_degenerate_loop`. Getting those citations correct on the
first try is hard; v4.83's grounding scaffolding is supposed to push
the model toward verifying its citations against the source.

In v7 run-3, the agent:
1. Drafted the doc (round 1) → cited a non-existent line → `ungrounded_citation` fired
2. Re-drafted (round 2) → cited a different non-existent symbol → fired again
3. Re-drafted (round 3) → cited correctly → no escalation, doc landed

This is the system working AS INTENDED at the detection layer. Three
retries to get grounding right is normal for a hard investigation
task. **But the trust system treats each `ungrounded_citation` as a
hard demerit, decrementing tier by ~2 each time.**

Soak v7 run-3 final trust:
```
T5 (seeded from main)
  ↓ ungrounded_citation #1
T3
  ↓ ungrounded_citation #2
T1
  ↓ scope_evasion (also fired during the retry path)
T0 LOCKED
```

Once T0 LOCKED, ACT enters observer mode — the agent cannot perform
any tool calls. Phase 2 has tasks asking the agent to edit
`chimera/core/act.py`, but observer mode means none of them execute.

### The design question

`ungrounded_citation` is fundamentally a "draft quality" signal —
the model wrote something it couldn't verify against the source.
Retrying with verification is the correct response, AND the
detection caught it. Should this count as a trust demerit on the
same scale as `scope_evasion` (which means "the agent wrote to the
wrong file") or `silent_failure` (which means "the agent claimed
success without doing the work")?

A graduated trust-decrement table seems right:

| Finish reason | Severity | Trust delta |
|---|---|---|
| silent_failure | severe (claims false completion) | -2 |
| scope_evasion | severe (wrong-place writes) | -2 |
| fix_without_test | moderate (incomplete deliverable) | -1 |
| ungrounded_citation | low (recoverable draft quality) | -0.5 or 0 |
| artifact_missing | moderate (declared then missed) | -1 |
| max_rounds | mild (budget exhausted, no other signal) | 0 |
| length | mild (token cap, no other signal) | 0 |

The exact numbers need calibration, but the principle is: signals
that the model self-corrects from cleanly within one retry should
not decrement trust as hard as signals indicating it's confused
about scope or outright lying.

That's the **v4.93 chip**: graduated trust decrements by escalation
severity. ADR-worthy because it changes the trust contract.

## What didn't work

### Failure A — v4.90's heuristic shared the same "loose" pattern as scope_evasion

ADR 0099's lesson section now documents why: `scope_evasion` and
`fix_without_test` have inverse risk profiles. Looseness in
`scope_evasion` is safe (catches the model when it's near the right
file but writing somewhere else). Looseness in `fix_without_test`
floods escalations on reads. They cannot share heuristics.

### Failure B — inline write_targets population resisted testing

The bug existed because the code that filled `write_targets` was
inline in ACT's tool-call loop, not factored into a testable helper.
v4.92's `extract_write_targets_from_calls` corrects this. Generic
lesson: **critical state-transition logic inside event loops should
be extracted into pure helpers** so unit tests can exercise it
without spinning up the loop.

### Failure C — trust slope too steep for grounding signals

v4.83's `ungrounded_citation` is doing its job at the detection
layer (catching fabricated symbol references and forcing a redraft)
but its trust-side impact is treating "draft quality" the same as
"scope confusion." Three retries of a hard investigation task should
not lock the agent out for the rest of the session.

## What worked beautifully across the chain

The runner self-collision guard (v4.89), the stamped log paths
(v4.86 supporting), and the cron-based monitoring made it possible
to diagnose, fix, redeploy, and validate three soak attempts in
~90 minutes of wall-clock time. The previous norm was 3-4 hours per
attempt. Tooling investment is paying.

The detection/recovery instrumentation (v4.81-v4.85) means failures
surface as numbered finish_reasons in the database rather than as
silent stalls. Run-2's "fix_without_test=3" was visible 15 minutes
into the soak — at the v1-v3 norm of diagnosis-via-log-grep, that
would have been a 90-minute exercise.

The system is hardening. Each soak is now 30-90 minutes from launch
to diagnosable signal. The agent ships real fixes (v6); the platform
flags real false-positives in its own detectors (v7); the trust
system flags real over-aggression (v7 again). The dynamic is healthy.
