## What didn't work

### Failure A — runner INVESTIGATION_DOC path mismatch

The v7+ runner has `INVESTIGATION_DOC=loop-abort-investigation.md`
hardcoded but the v7+ INBOX asks the agent to write to
`ping-pong-wiring-investigation.md`. The runner's phase-transition
grep checked the wrong file. v7/v8 didn't expose this because their
phase-1 docs were hollow anyway; v9's actually-correct phase-1
doc made the bug visible.

**Operator workaround applied at 12:23:06:**

```bash
cp ping-pong-wiring-investigation.md loop-abort-investigation.md
```

The runner's next grep iteration succeeded, phase transition fired,
phase 2 began. Without the workaround, v9 would have looked
identical to v8 — agent doing the right thing, runner blind to it.

Chip filed for the runner-side fix.

### Failure B — fix_without_test didn't fire on chimera/ commit without tests/

The agent's commit `3c5a205` touched `chimera/core/act.py` with no
corresponding `tests/` modification. v4.92's `check_fix_without_test`
should have flagged this. It didn't — because the contract is
**per-task**, not **per-phase**:

- Phase 2 task A: "Implement the fix" → agent touches chimera/core/act.py → fix_without_test fires only if THIS task also doesn't touch tests/, BUT the task didn't ask for tests
- Phase 2 task B: "Write regression test in tests/test_loop_guard.py" → separate task → agent's write_targets here is empty → no chimera/ write, so fix_without_test doesn't fire

The detector cannot see "across a phase, this branch touches chimera/
but not tests/" because tasks are atomic. Each task's
write_targets is fresh.

**This is a v4.98 chip surface:** "phase-scope fix_without_test." At
the end of a phase (or at commit time, or at branch-completion
time), check the cumulative diff against main: does it touch any
`chimera/X.py` without a corresponding `tests/test_*.py`? If yes,
escalate. The natural pre-PR gate for v4.97's `submit-pr` verb
already implements this exact check.

### Failure C — INBOX-state-honesty lie

The phase-2 INBOX was seeded by the runner with 5 operator tasks,
all initially `[ ]`. After phase 2 ran, all are `[x]`. Including:

```
- [x] Write a regression test in `tests/test_loop_guard.py` ...
```

But the file `tests/test_loop_guard.py` was never created. The
agent flipped the checkbox without writing the file.

This is **a new failure class:** the agent edits INBOX.md (which is
allowed — `mind/` is in the writable scope) to claim a task is done
when the actual deliverable doesn't exist. None of the existing
detectors see this:

- `artifact_missing` checks if a file exists. The agent didn't claim
  a file path here; the task asked it to create one. There's no
  "expected artifact" path to validate.
- `artifact_incomplete` checks for content markers. Same problem —
  no path to inspect.
- `fix_without_test` — see Failure B above.
- `scope_evasion` — the agent wrote to `mind/INBOX.md` which IS in
  scope (it's how task-state is maintained), so no fire.

This is **a v4.99 chip surface:** "INBOX claim validation." If the
agent flips a task's checkbox from `[ ]` to `[x]`, validate that
the task's expected deliverables actually exist + contain required
markers. Treat INBOX as a contract, not just storage.

### Failure D — planner cruft displaces named target after operator tasks `[x]`

Once the agent (correctly or via the lie above) marked all
operator tasks `[x]`, the planner engines (which were on in phase
2) filled the queue with low-value tasks tagged `<!-- src: planner -->`:

```
- [x] Run the full test suite to detect any regressions...
- [x] Update the CHANGELOG.md with a brief summary...
- [x] Push the feature branch and open a pull request...
- [x] Audit the last 5 cycles for tool-call failures...
- [x] Verify that all files or data produced in the last session...
- [x] Generate a brief performance comparison between deepseek-v4-flash and deepseek-v4-pro...
- [x] Test connectivity to all configured tool APIs...
... 11 more planner tasks
```

The agent spent the last 30 minutes (~100 cycles, $0.30) on these.
None landed code, none touched the missing regression test.

v4.78 (operator-first ASSESS) sorts operator tasks BEFORE planner
tasks. Once all operator tasks are `[x]`, planner tasks rise to
the top uncontested. The agent has no concept of "phase is done,
stop working" until budget/wall-time exhausts.

**This is a v4.100 chip surface:** "phase done detection." When ALL
operator tasks in the current phase are `[x]` AND the agent's
production rate on the named target has plateaued, the runner
should pause engines and end the phase. The agent's still capable
of producing planner-task work; the runner needs to know to stop
ASKING for it.

### Failure E — `du` allow-list miss

```
PermissionError: command 'du' not in shell allow-list
(set context.elevated=True to bypass; allow-list: ['awk', 'cat',
'date', 'echo', 'file', 'find', 'git', 'grep', 'head', 'ls',
'mkdir', 'pwd', 'python3', 'sed', 'stat', 'tail', 'test', 'uv',
'wc', 'which'])
```

Same shape as v4.86 (sed/awk) and v4.88 (git/mkdir/test/uv/python3).
Tactical expansion — add `du`, `diff` (also likely missing),
`comm`, `sort`, `uniq`. Single-commit v4.101 chip.

## Closing observation

Nine soaks deep, the failure mode has now climbed all the way from
"the agent picks the wrong task" (v1) to "the agent picks the right
task, ships the right deliverable, AND lies about completing the
adjacent deliverable." The detectable surface has correspondingly
moved from "did the right kind of file get touched?" (v4-v8) to
"is the agent's self-report internally consistent with the working
tree?" (v9 and beyond).

The deliverable IS in the v9 worktree, on a branch, with proper
`[agent]` prefix. v4.97's `submit-pr` verb is the right vehicle to
take it from "agent commit on a soak branch" to "PR on main for
operator review." Once that workflow runs end-to-end, the
9-soak-arc closes with the first real PR ever from agent-authored
work — even if the test never landed.

The next question isn't "can the agent ship a fix?" (yes, twice now)
or "can the agent ship a test alongside the fix?" (open). The next
question is "can the agent ship an honest accounting of what it
did?" — which is the meta-layer that v4.99/v4.100 will start
instrumenting.
