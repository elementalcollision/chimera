**Subject:** Interventional long-cycle test for the
`degenerate_loop_abort` hot signature from soak v1.
**Operator decision:** Stopped early at $0.28 / $20 budget.
The deliverable (a `loop_guard.py` fix) was not produced, but
**five soak findings landed that more than pay back the spend.**
Two are confirmations of v4.74 design choices; three are new
operator-visible failure modes worth shipping.

## What the test set out to do

Run a multi-hour interventional test with three properties:
- Sandboxed git worktree (chimera/* editable, no push)
- Two budgets: $10 research + $10 remediation, separate watchdogs
- Named target: investigate the `degenerate_loop_abort` hot signature
  from soak v1 and prototype a fix

Design doc: `mind/long_cycle_test_plan_v2_2026-05-20.md`.

## What actually happened

### Bootstrap (15:24–15:28 PDT)

Worktree created cleanly at `/Users/dave/chimera-soak-2026-05-20-2224`
on branch `chimera-soak/2026-05-20-2224`. Origin remote removed. Fresh
`state/chimera.db`. INBOX seeded with the focused phase-1 task.

**Finding #3 — orphan WAL.** When trying to spot-check progress
*before* the v2 runner launched, the Next.js dashboard threw
`SqliteError: file is not a database`. Diagnosis: a 4.1 MB WAL file
left orphaned in `state/chimera.db-wal` after `pkill -9` killed soak
v1's mid-cycle `chimera run`. SQLite's better-sqlite3 can't reconcile
main + uncheckpointed WAL in read-only mode and emits a misleading
error (the file IS a database; the WAL just needs checkpointing).
Fix: `sqlite3 state/chimera.db "PRAGMA wal_checkpoint(TRUNCATE);"`.
All 1963 api_calls and 13 mutations from soak v1 were intact —
nothing was actually lost.

This failure mode is silent and confusing. Operator wouldn't have
caught it without opening the dashboard. Follow-up filed to teach
`chimera doctor` to detect orphan WALs and to add a SIGTERM atexit
handler that checkpoints cleanly. (Confusion budget: ~30 seconds
during a live test.)

### First launch attempt (15:24–15:27)

Runner up, ACT loop running, but every cycle emitted:

```
ACT: LOCKED at T0; observer mode (skipping 6 task(s))
```

**Finding #4 — fresh-worktree T0 lock.** The runner's `rm -f
state/*.json` wiped `trust_state.json` along with the
graph-projection snapshot. TrustManager (v1.3) defaulted the agent
to T0 (LOCKED). The agent sat in observer mode for 18+ minutes
across multiple iterations, completing no ACT tasks while the
watchdog kept incrementing iter counts.

Fix: copy `trust_state.json` and `tiers.json` from main into the
worktree's state/ before the loop starts. The runner now does this;
follow-up filed for `chimera trust promote` CLI + `chimera doctor`
warning when the agent is at T0 with > 5 completed observation
cycles.

This is a real gotcha for anyone bootstrapping Chimera into a new
environment. The trust ladder was designed for fresh-install
gradual trust-building; operator-restored worktrees shouldn't have
to climb it again.

### Second launch (15:27–15:54)

Reused the existing worktree (idempotent runner fix), seeded T5
trust state, 18 iterations over 22 minutes.

**Finding #1 — session-mode validated:**

```sql
SELECT engine, status, COUNT(*) FROM engine_runs GROUP BY engine, status;
  discovery|success|1
  curiosity|success|1
  reflection|success|1
```

Compare soak v1 (UTC-window mode): `curiosity|skipped|54`,
`reflection|skipped|<all the rest>`. v4.74 ADR 0092 with
`CHIMERA_ENGINE_SESSION_MODE=1` produced exactly the rotation the
post-mortem hypothesised — first cycle ran Discovery (priority head,
gated by signal-density but admitted after some api_calls
accumulated), second ran Curiosity, third ran Reflection. Then
dedup kicked in and no engine fired again. Clean.

**Finding #2 — cwd L-2 fix held.** No `mind/mind/*` paths appeared
anywhere in the worktree filesystem. v4.74's port of shell.py's
v4.4 L-2 fix is correctly in force for code_exec.

**Finding #5 — phantom completion:**

```
ACT: 'Write all of the above to' → max_rounds (rounds=12, tools=16, completed=False)
ACT: 'Write all of the above to' → stop          (rounds=2,  tools=2,  completed=True)
```

The second attempt reports `completed=True`, but
`mind/research/loop-abort-investigation.md` does not exist. The
model emitted `stop_reason=stop` without producing the artifact.
ACT trusts the model's stop signal as "task done." When the
operator's INBOX promises a file at a specific path, ACT should
**validate that the file exists** before flagging completed.

The v4.3 / ADR 0066 artifact-verification pattern already exists in
the codebase for a related case — port that logic to ACT. Follow-up
filed.

**Finding #6 — INBOX provenance:**

After completing 5 of 7 phase-1 INBOX tasks (read loop_guard.py,
read act.py, search chronicle, hypothesise, spawn sub-agent), and
falsely "completing" the write-artifact task, the agent then
pivoted to:

```
ACT: 'Audit tool invocation success rates and latency trends from cycles 120-139…'
ACT: 'Compile a retrospective summary of the last 10 cycles…'
ACT: 'Define a primary objective for this session…'
ACT: 'Verify operational status of all integrated tools and models…'
```

These are well-formed tasks — but **none of them are the operator's
phase-1 work.** They came from the Reflection/Discovery engines
appending their suggested follow-ups to INBOX.md. ASSESS reads INBOX
top-to-bottom with no notion of provenance: operator-authored
bullets and engine-proposed bullets sort equally.

The cascade is subtle:
1. v4.74 session-mode lets all three engines fire (good!)
2. The engines write follow-on tasks to INBOX (their normal job)
3. ASSESS picks the next "open" task without checking who wrote it
4. The agent works on engine-proposed tasks
5. Operator's original work never finishes
6. Watchdog burns through phase-1 budget on engine drift

This is the cost of v4.74 working: it activates a latent design gap
that was hidden when only one engine ever fired per session.

Follow-up filed: provenance comment tags on engine-appended INBOX
rows + ASSESS sort that puts operator-authored tasks first.

### Stop (15:54 PDT)

Operator decision: stop, file findings, write post-mortem. Total
spend $0.28 / $20 across 117 api_calls and 19 cycles.

## What the next soak should look like

Soak v3 should retry the `degenerate_loop_abort` target once #4
(INBOX priority) ships. Tighter scope:

1. Same worktree setup, with the trust-state seed fix already in
   the runner.
2. Disable engines for phase 1 entirely
   (`CHIMERA_ENGINES_ENABLED=0`) so the operator's INBOX runs
   uncontested. Engines come back on in phase 2 (when the
   investigation doc is in hand and the agent is editing code).
3. Use the new artifact-validation logic (#3) so a phantom
   completion doesn't pass.
4. Phase-1 budget should be tighter: ~$3, not $10. Soak v2's data
   suggests the investigation work is cheap ($0.28 burned 5
   subtasks); the previous $10 cap was an overestimate.

Estimated soak v3 budget: $5 research + $5 remediation = $10 total.

## What I learned about the test pattern itself

Soak v1 was observational, soak v2 was interventional. Soak v2 produced
**more findings per dollar** ($0.28 → 4 follow-ups vs soak v1's
$3.04 → 2 follow-ups + 1 confirmation), and the findings are
sharper because they're failure-mode findings, not research-result
findings.

The cost of going interventional: the soak's *named target* is at
the mercy of the agent's emergent behaviour. Soak v2 didn't fix
`loop_guard.py`. But the things it found are higher-leverage than
the target would have been.

The interventional pattern is worth keeping in the rotation. **Just
budget for the meta-findings, not just the deliverable.**
