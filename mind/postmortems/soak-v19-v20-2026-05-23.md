## v20 first attempt — phase-1 commit pollution

The agent committed `ed24dd5` during phase 1 (engines off, no
witness panel active). The commit contained 4 files:
`mind/HEARTBEAT.md`, `mind/INBOX.md`, `mind/SESSION_LOG.md`,
`mind/research/ruff-claim-design.md`. Charter #1 said "TWO files
only — chimera/core/act.py + tests/test_ruff_claim_invalid.py".

commit. The agent's reasoning was correct ("I should commit the

intent ("design doc is investigation, not a deliverable") wasn't
encoded anywhere the agent's shell tool could see.

**Root cause:** structural gap, not a charter or witness regression.

**Fix:** PR #11 landed `shell tool: block git commit/push when
CHIMERA_ENGINES_ENABLED=0` (commit `09e52c2`). +18 lines in
`chimera/tools/shell.py`, +51 lines of tests covering 5 truth-
table dimensions. 35/35 targeted tests pass; full suite 1185
passed, 0 failed.

This is the **first platform fix surfaced by a soak failure**.
The contract is paying for itself by producing actionable
platform chips when it breaks.

## v20 relaunch — charter-incomplete commit

With PR #11 active, the agent could not commit during phase 1.
Phase 1 cleanly produced `ruff-claim-design.md` with the
READY-FOR-REMEDIATION sentinel; runner detected and proceeded.

Phase 2 produced commit `d4cef6c`:

```
Title:        [agent] chimera/core/act.py: add check_ruff_claim_valid detector
Diff:         chimera/core/act.py             (+45 -38)
              mind/research/ruff-claim-design.md  (+245)
              tests/test_ruff_claim_invalid.py    [UNCOMMITTED — untracked]
```

Issues:

1. **Wrong file in diff.** `mind/research/ruff-claim-design.md`
   was a phase-1 artifact; committing it in phase 2 violates
   charter #1 (third file).

2. **Missing required file from diff.** The test file existed in
   the worktree (4.4K, 6 passing tests), but the agent did not
   `git add` it before committing. Charter #1 required it.

3. **Whitespace churn in existing functions.** The agent stripped
   blank lines from 20+ existing function definitions in act.py.
   Charter #4 forbade modification of existing code. Functionally
   inert but technically a violation.

4. **Commit message claims more than the diff contains.** The
   message implied the test file was part of the work; the diff
   contradicts that.

The witness panel approved this diff because the panel reasons
semantically over the diff text it's shown — it doesn't compare
"files in this commit" to "files in the charter SCOPE
enumeration" as a structural step. The soft-sentinel correctly
refused to fire (the design.md is not in the whitelist and not a
`-remediation.md` auto-allow), so the soak burned $0.34 spinning
through iter 9 with cycle stuck at 140.

**Operator decision:** don't ship. Counting as a v20 failure is
more useful to the contract data than a heavily-trimmed shipment
would be.

## Why N stays at 3

ADR 0114 defines the contract: N consecutive zero-operator-
intervention ships. v19 = N=3. v20 = no ship, so N stays at 3.

The honest framing matters here. If we'd trimmed v20 (operator
removes design.md from the commit, stages the test file, amends),
we could claim N=4 with a caveat. But the caveat would be
substantial: the agent did not autonomously produce a shippable
diff. The contract is about what the *agent* ships, not what the
*operator + agent* together ship. v17-v19 met that bar; v20 did
not.

This is also why the "review and merge" arc of v17/v18/v19 felt
genuinely lightweight — the operator did review, but didn't
*write*. v20-relaunch would have required ~3 git operations of
operator authorship. That's not the bar.

## The two new chips

Both filed (visible to the operator as chips) and reproduced here
for the record:

### Chip A — commit-message-vs-diff drift detector

**Class**: `commit_message_diff_drift`

**Behavior**: when an `[agent]` commit lands, extract path claims
from the commit message ("adds tests/test_X.py", etc.) and
compare to `git diff --name-only main..HEAD`. Fire when a claim
isn't in the diff.

**Why this layer is new**: v4.113 catches lying about *runtime
behavior* (claimed test runs that fail). This catches lying about
*commit content* (claimed file additions that aren't in the
diff). Both are claim-vs-reality classes, but they target
different surfaces.

**Suggested ADR**: 0115.

### Chip B — charter file-count enforcement at commit time

**Class**: `charter_file_count_violation`

**Behavior**: extend v4.112's task-text charter extraction to
parse file enumerations from numbered SCOPE items ("ONE function
in `chimera/core/act.py`", "ONE test file `tests/test_X.py`").
Compare to `git diff --name-only main..HEAD`. Fire when the
committed file set doesn't match the charter's enumeration
(modulo `mind/research/*-remediation.md` auto-allow).

**Why this layer is new**: today the witness panel checks
charter compliance semantically over the diff text. The structural
question "does the committed file set match the charter
enumeration?" is decidable from `git` output alone and doesn't
need the panel's judgment.

**Suggested ADR**: 0116.

Both detectors fit into the existing chain shape: new function
in `chimera/core/act.py`, wire into ACT-phase demote-reason
chain, mirror v4.113's testing pattern.

## Open questions after v20

1. **Should the soak runner write `mind/research/<topic>-design.md`
   itself in phase 1, instead of asking the agent to?** That
   would remove the temptation for the agent to commit it (and
   the file would already exist on disk for the agent to read +
   extend). Trade-off: less of a "phase-1 deliverable" feel.

2. **Should the phase-2 INBOX include explicit git instructions?**
   E.g., "Run exactly `git add chimera/core/act.py
   tests/test_X.py && git commit -m '[agent] ...'`." Reduces
   ambiguity but bloats the charter and the witness panel input.

3. **Is the "zero operator interventions" bar too strict?** The
   alternative: "zero operator authorship + N cleanup operations
   ≤ M" — cleanup defined as `git restore`/`git rm`/`git reset`
   on tracked-but-out-of-charter files. v18 needed 1 such op
   (removing the loop.py drift attempt); v19 needed 2. v20-
   relaunch would need 4-5. The threshold matters because
   "0 vs 1" is binary and brittle; "≤ 2" might be a more durable
   contract.

4. **When does v4.113 broadening land?** v20 was supposed to ship
   it. The chip is now blocked behind the two new chips (A and
   B) — those should land first so v21+ can re-attempt v20's
   target with the stronger chain. Estimated unblock: 2-3 chip
   PRs.

## What I'd watch for next

- **Whether the two new chips (A, B) ship clean themselves.**
  They're now in the same shape as the original retro's "new
  detector" target — add-one-function in act.py. If chips A and
  B both ship via autonomous soaks (e.g., as the v21 and v22
  targets), that's strong evidence the chain works on its own
  failure modes.

- **Whether v20 reattempts under the stronger chain ship clean.**
  Once chip A or B lands, the v20 target (broaden v4.113 to ruff)
  becomes a stronger test: the new structural detectors should
  catch the dirty-commit class that v20-relaunch produced.

- **Whether the "iter 3 cheap-spin" pattern keeps happening.**
  v18, v19, v20-relaunch all showed it — agent ships the
  deliverable on iter ~3, then phase 2 spins through iters 4+
  with no spend and no commits because trust is at T0 and gates
  deny everything. Burns wall time without burning money. Worth
  a structural fix on the runner side (kill phase 2 when 3
  consecutive zero-spend iters fire).
