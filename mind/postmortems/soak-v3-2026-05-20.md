## What actually happened

### Phase 1 ran for ~22 minutes / $0.45 across 4 cycles

```sql
SELECT finish_reason, COUNT(*) FROM ACT outcomes:
  Read loop_guard.py        → stop completed=True  (2 rounds)
  Read call site in act.py  → stop completed=True  (7 rounds)
  Form a verdict            → max_rounds  ×3
  Form a verdict            → stop completed=True  (4th attempt, 18 rounds)
  Write all of the above to → stop completed=True  (1 round, 0 tools)
```

The two read tasks completed cheaply. The verdict task chewed through
three full max-rounds attempts (12, 18, 7 rounds with `length` stop
once) before finally producing a verdict on the fourth attempt at 18
rounds. Then the write task completed in **1 round with 0 tool calls** —
and the file was never written.

### Finding 5 (most important): v4.79 didn't fire

The investigation doc `mind/research/loop-abort-investigation.md` does
**not exist** in the worktree, but ACT recorded `completed=True` for
the "Write all of the above to..." task. The `task_escalations` table
shows only `max_rounds: 2` entries — **zero `artifact_missing`
entries**.

v4.79 / ADR 0093 was built specifically to catch this. The INBOX
bullet contains the path in both forms v4.79's `expected_artifacts()`
is supposed to handle:

- Backtick form: `` `mind/research/loop-abort-investigation.md` ``
- NL form: `Write all of the above to ...`

Two hypotheses (in the filed chip):

1. **Code-path bypass.** Some condition in `chimera/core/act.py`
   skips `check_artifacts()` for this task shape — maybe early
   return on `stop_reason="stop"`, maybe a tier gate, maybe the
   check runs against a different field than the full task text.
2. **Regex/path-extraction failure.** The INBOX bullet is multi-line.
   The "to" verb and the path are on separate lines. If
   `expected_artifacts()` parses line-by-line, the cross-line match
   fails. Or ACT may pass only the task's *label* (truncated to the
   first line, visible in logs as `'Write all of the above to'`)
   instead of the full description — the regex would have nothing
   to match against.

This is the soak's most important output. v4.79 was released this
afternoon to fix exactly this regression; v3 reproduced the regression
within 22 minutes against the v4.79-released code. The chip is filed
with a reproduction strategy.

### Finding 4: rg-not-installed (already shipped as v4.80)

The model called `rg` (in the shell allow-list) and got
`FileNotFoundError: program not found on PATH: rg` because ripgrep
isn't installed on this macOS. ACT absorbed the error as an
observation; the model adapted; rounds were burned. v4.80 ships a
runtime `shutil.which()` filter that trims the allow-list at import,
plus a `chimera doctor` warning when an allowed tool is missing.

### Finding 1: v4.77 worked silently

When the runner was killed (`pkill -INT` then `-9`), the v4.77 atexit
handler ran `PRAGMA wal_checkpoint(TRUNCATE)` cleanly — the
worktree's `chimera.db-wal` was already 0 bytes when I checked it
post-mortem. No orphan WAL to recover. Soak v2's finding #3 is fixed
end-to-end.

### Finding 2: engines-off kept phase 1 on-task

Phase 1 ran with `CHIMERA_ENGINES_ENABLED=0`. ACT executed the 4
operator-authored phase-1 bullets in order without pivoting to
engine-proposed work. The engines wrote nothing because they didn't
fire. This is the simplest possible validation of the soak-v2
diagnosis: with engines silenced, INBOX displacement doesn't happen.

(v4.78 alone would have handled it too — operator tasks sort first
via provenance — but belt-and-suspenders.)

### Finding 6: ACT decomposition gap on "Form verdict"

The "Form verdict" task hit `max_rounds` three times in a row before
the fourth attempt produced a verdict. Each retry consumed up to 18
rounds and 25-34 tool calls. This may be:

- Task too vague for one ACT loop — should be decomposed into "draft
  verdict → critique draft → finalise"
- Model getting stuck in research mode (re-reading source files
  repeatedly) rather than synthesising
- v4.65 task splitter not picking this up because the proposal
  threshold isn't hit

Worth investigating but lower priority than #5.

### Finding 7: the pattern

Three consecutive soaks (v1 observational, v2 interventional,
v3 focused remediation) have produced **zero code-change deliverables**
against their named targets. Each has produced *meta-findings* — gaps
in the framework itself — that are arguably more valuable than the
named target would have been. But the explicit "interventional"
promise (agent ships a fix) hasn't been kept.

Reading the data: in v1/v2/v3 combined, the agent successfully read
the relevant source code, formed a verdict (eventually), and stopped
at "writing the artifact" — the same step every time. Soak v3 makes
this very specific: it's the **write-the-output step** that fails,
not the analysis. And v4.79 was the fix for that step, and v4.79
didn't fire.

So the chain is:
- Analysis layer: works
- Synthesis layer: works (slow, but produces a verdict)
- **Artifact write: fails silently with `completed=True`**
- Validation layer (v4.79): didn't catch the silent failure

Until v4.79 actually catches this, every soak will stall at the same
step. Fix #5 first, then any future soak has a real shot.

## What I learned about the soak pattern

Soak v3 confirms a hypothesis from soak v2's post-mortem:
**interventional soaks produce more findings per dollar than
observational ones**, but the named-target deliverable is at the
mercy of whichever layer is most broken. In soak v3's case, that
layer was v4.79 itself — the patch that was supposed to fix the
problem.

This is a useful failure mode. It means the soak pattern is acting
as a real integration test of the most recently shipped behaviour,
not just a research-output generator. Every soak that doesn't ship
its deliverable is doing the same job as a failed CI run — it's
telling you something specific is broken.

Future soaks should be planned with the **expectation** that they
expose the latest release's blind spots, not deliver a patch to the
named target. The named target is just the workload that surfaces
the gap.
