# ADR Revisits — Would I Still Write This Today?

## ADR 0001 — SDK Chimera Boundaries

**Would I still write this today?** Mostly yes, but the "per-concern ownership" table has aged quickly. The decision to re-implement every pattern (Hermes registry, OpenClaw dispatch, Village KFM) as fresh `chimera/` code was right for Phase 0 — it forced deep understanding and kept dependencies minimal. But today I'd be more honest about the maintenance tax. The Hermes-style `registry.register()` with AST auto-discovery and TTL-cached `check_fn` is clever but over-engineered for 12 tools. I'd swap it for a flat dict-of-dicts and let a weekly refactor round push complexity up only when tool count hits 50+. The biggest miss: the Reggio loop (ADR 0003) is referenced as an "open input" but the boundary document never revisits how a feedback loop changes tool dispatch policy. If I wrote this today, goal→tool coupling would be a first-class concern, not a deferred follow-up. The module layout diagram is still useful as a map, but the `chimera/proposals/` directory gathered dust for weeks — proposal generation never reached the critical cadence that justified its own package. I'd merge it into `core/` as a handful of functions.

## ADR 0002 — Memory Strategy

**Would I still write this today?** The SQLite-first call was correct and I'd make it again. But the four-store taxonomy (ontology / activity log / drift state / episodic recall) feels like a design-doc purity that the runtime never fully inhabited. In practice, the ontology `entities` table and the `entity_transitions` table do 95% of the work; the activity log (`agent_activity_log`) saw low write volume and could have been a simple append-only JSONL file with cheaper querying via `grep`. I'd demote it from "dedicated SQL table with Alembic migration" to "file with a thin reader." The biggest regret: deferring episodic recall entirely. The "no use case yet" argument was conservative to the point of timidness — even a naive `mind/` grep-for-keywords would have given us a recall baseline to iterate on. Waiting for embeddings created a vacuum where no retrieval existed at all. Today I'd add a dirt-simple full-text search on `mind/wiki/` markdown files (SQLite FTS5, zero dependencies) as a Day-1 feature and let the vector store earn its keep later. The v1+ Postgres migration trigger conditions are still sound, but I'd add a softer trigger: "when the SQLite WAL file grows past 512 MB in normal operation."

## ADR 0015 — LadybugDB Graph Store

**Would I still write this today?** Honestly? Probably not, or at least not as a core dependency so early. LadybugDB (née Kuzu) is impressive tech — columnar Cypher execution, HNSW vectors, tidy Python bindings. But the gap between "six nice-to-have graph queries" and "must ship a Ladybug container volume" is wider than this ADR admits. The five SQLite-recursive-CTE use cases (entity lifecycle, mutation provenance, peer trust, skill deps, wiki links) all work at MVP scale with queries under 50 lines. The sixth — vector recall — was explicitly deferred. So what, exactly, is Ladybug doing for us that `WITH RECURSIVE` doesn't? The skill-dependency and wiki-cross-reference stores are genuinely graph-only, but both are small enough to keep as JSON adjacency lists read at boot. The CLI surface (`chimera graph init`, `rebuild`, `query`) is nice but got used maybe twice outside testing. Today I'd make the graph an **optional** projection — `chimera graph build` exists for when you want Cypher-level expressiveness, but the default path uses SQLite + adjacency JSON. I'd also be sharper about the Ladybug/Kuzu saga: Apple archived upstream Kuzu in October 2025, the Ladybug rebrand was in flux, and pinning to `kuzu>=0.10` assumed a continuity that wasn't guaranteed. Today I'd wait for a stable Ladybug release or commit to Kuzu 0.9.x as a frozen fork.
